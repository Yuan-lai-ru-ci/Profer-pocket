# 流式正文的分块：稳定前缀 + 尾块

> 日期：2026-11-05
> 范围：`android-native/` 的助手正文渲染（Agent 对话页与 Chat 页）。
> 起因：用户问「移动版输出的内容是不是没有渲染成整体的块，而是每次都要重新渲染」。

## 1. 原来怎么做的

流式帧里的 `partial` 带的是**累计全文**（不是增量），`ChatReducer` 每帧用新正文替换这条
assistant entry，`UiMapping.projectEntry` 再对新正文调 `cachedRichBlocks(entry.text)`：

- 整条正文从头重新分块——代价随正文长度线性增长；
- 缓存以**全文**为 key，流式每帧一个新 key：几十秒就把 512 条上限填满，
  里面全是永远命中不了的半成品正文，然后整表清空，顺手把历史消息的缓存也清掉；
- Chat 页（`ConversationScreen`）同样每帧整条解析，而且是在主线程。

好消息是渲染层本来就不是整屏重画：消息投影按 `entry.id` + 实例身份命中缓存，
`LazyColumn` 以 `id` 为 key，历史消息连 `ChatMessage` 实例都复用。所以问题只在
「解析」这一层，不在「渲染」这一层。

## 2. 现在的做法

### 2.1 解析器带块偏移

`parseRichBlocksFrom(raw, from)` 返回 `RichParse(blocks, starts)`，`starts[i]` 是第 i 块
起始行在原文中的字符偏移。块的边界处所有累加器都是空的，因此**从任意一块的行首起算，
与整段解析等价**——这是增量解析成立的前提。

### 2.2 流式只重算尾块

`streamingRichBlocks(messageId, text)` 按消息记住上一次的解析结果：

- 正文以旧文开头 → 保留前 N-1 块，从尾块行首重算；
- 正文被重写（不再以旧文开头）→ 退回整条解析；
- 中间态单独存放，最多 4 条，**不写进**已完成消息的缓存。

有一条例外要处理：最后一行还没收到换行时，它现在可能被当成普通段落（`- `、`|`、`1.`、`` ` ``），
再长一个字就变成列表/表格/围栏，而这种变化会把**上一块**也带进来重新归类
（`- 第一条` / `- ` 两段在下一帧会并成一个列表）。所以尾行以标记字符开头时，稳定前缀再退一块。
这条是逐字前缀对照测试抓出来的，不是推测。

### 2.3 缓存

- 已完成消息：`LinkedHashMap` 按访问顺序做 LRU，满 256 条淘汰最久未用的一条（不再整表清空）；
- 流式收尾那一帧调 `settleStreamingRichBlocks`，把尾帧结果**转正**进已完成缓存，
  省掉收尾时的一次整条重算，同时释放中间态。

### 2.4 块级跳过

`ContentBlock` 的每个实现都补了 `@Immutable`：接口上的注解不会传给实现类，
带 `List` 字段的数据类会被 Compose 判成不稳定，流式时表格/列表块每次重组都会重走组合。

## 3. 量级

JVM 基准（非 ART 实机）：4.5KB 正文

| | 每次更新 |
|---|---|
| 整条解析 | ~200µs |
| 增量（只算尾块） | ~1.9µs |

约 100×。按 32ms 采样（约 31Hz），一段 4.5KB 回复的解析开销从每秒 ~6ms 降到 ~0.06ms。

## 4. 验证

- **解析等价性（最硬的一条）**：把 HEAD 版 `parseRichBlocks` 原样拷进一个临时测试，对 38 份语料
  （空文档、CRLF、未闭合围栏、半张表格、行尾空格、`- ` / `1.` / `|` / ```` ``` ```` 这类半截标记行、
  混合结构）逐个比对新旧实现的输出，再对每份语料的**每一个字符前缀**比一遍——全部相等。
  这条验完即删，没进仓库。
- `feature:chat` 单测 63 项 0 失败，新增：
  - 逐字前缀对照：一份含标题/段落/列表/有序列表/引用/表格/围栏的正文，按**每一个字符前缀**
    分别走增量解析与整条解析，结果必须逐项相等（LF 与 CRLF 各一轮）；
  - 稳定前缀必须是同一批块实例（证明真的复用了，而不是重算后恰好相等）；
  - 重写正文退回整条解析；
  - 流式中间态不写进已完成缓存；收尾转正并释放中间态；
  - 半张表格先按段落渲染、收全后变成表格。
- `app` 单测 51 项 0 失败；`:app:assembleDebug` 成功。
- 模拟器实拍（debug 画廊）：`page=conversation` 走的是 `ProferRichText` → `cachedRichBlocks`
  这条真实链路，标题/列表/段落排版正常；`page=chat` 的流式光标与工具卡正常。
- **未做**：真机接桌面端的真实流式帧率/掉帧对比。解析耗时已量化，重组与布局的收益要靠实机确认。

## 5. 仍然存在的行为（不是缺陷）

半张表格、未闭合的代码围栏、没闭合的 `**` 在收到下一帧前仍会先按段落/纯文本显示，收全后翻型。
这是「解析是当前正文的纯函数」的必然结果，和本次优化无关；要做成不翻型，需要让解析器对未闭合
结构做前瞻（代价是解析器复杂度，收益有限）。
